# 按需个股分析与版本化缓存设计

## 背景

当前网页首屏依次请求股票池和默认个股。冷启动实测 `/api/universe`
约需 88.64 秒，随后个股接口仍会长时间计算。主要原因是股票池同步重算
严格 VCP、紧密平台和支撑压力相关图表行；个股因子横截面又会为同日
peers 重复执行完整 `build_chart_rows()`。

本阶段目标是恢复网页可用性，同时避免与正在开发的高位风险模型产生
大范围接口冲突。

## 方案选择

采用保持现有 API 合约的阶段 A：

1. 股票池只实时计算轻量摘要，不再为全部股票同步重放 VCP、平台和支撑压力。
2. 重型结构只在访问具体股票时计算。
3. 横截面 peers 只计算明确允许排名的数值因子；这些因子必须使用轻量直接算法，
   不得间接触发完整图表构建。
4. 股票池和因子原始值使用数据库版本、观察日期、股票代码和算法版本组成缓存键。
5. 数据更新通过数据库 revision 自动切换缓存命名空间，不复用旧行情结果。

暂不拆分前端接口，也不在本阶段建立新的持久化分析表。这样可以最小化 API 和
UI 改动；持久化缓存及渐进加载作为后续阶段。

## 数据流

### 股票池

`/api/universe` 读取一次批量历史快照，只计算：

- 最新日期和新鲜度；
- 多尺度动量横截面；
- 63 日实现波动率；
- 已有的缓存形态摘要（若没有则明确为不可用）。

严格 VCP、紧密平台和近端枢轴不得在首屏请求中为全市场现场计算。股票池响应以
`(database_revision, asof, universe_summary_version)` 缓存。相同版本的并发或重复
请求复用同一结果。

### 个股详情

访问 `/api/stocks/<ticker>` 时：

- 当前股票完整计算一次图表、支撑压力、VCP、反转、风险和模型输出；
- peers 只提供横截面排名需要的轻量原始数值；
- `close_vs_ema20_pct`、`close_vs_sma50_pct`、`close_vs_sma200_pct`、
  `pivot_distance_pct` 和 `volume_ratio` 改为直接从 OHLCV 尾部计算，
  不调用 `build_chart_rows()`；
- 结构布尔值、结构计数和解释型对象继续只计算当前股票。

因子缓存键为：

```text
(database_revision, factor_key, factor_version, ticker, observation_date)
```

缓存有界，返回不可变/复制后的 JSON 安全值。数据库版本变化时旧命名空间不再命中。

## 兼容性与状态

- 现有 `/api/universe` 和 `/api/stocks/<ticker>` JSON 字段保持存在。
- 尚未计算的股票池形态使用不可用状态，不伪造 `false`。
- 个股页仍返回完整结构和模型输出。
- 更新任务进行期间沿用现有预测不可用语义。
- 缓存不跨算法版本，避免代码升级后返回旧解释。

## 并发和错误

- 相同缓存键只允许一个计算执行，后续请求等待同一结果。
- 计算失败不写入成功缓存；现有安全错误封装保持不变。
- 缓存必须有大小上限，避免 194 只股票和历史日期无限增长。
- 所有历史计算继续只使用观察日及以前的数据。

## 验收

- `/api/universe` 冷启动不调用 VCP、紧密平台或 `build_chart_rows`。
- 个股详情的完整图表构建次数不随 peer 数量线性增长。
- 同一数据库版本下重复请求命中缓存。
- 数据库 revision 变化后不命中旧缓存。
- 股票池目标响应时间低于 5 秒；缓存个股目标低于 1 秒。
- 现有 API 合约测试、前端运行时测试和完整 Python 测试保持通过。

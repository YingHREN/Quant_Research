## P0 — 持久化预测产物缓存（PERF-002）

设计文档：`docs/superpowers/specs/2026-07-26-persistent-forecast-artifact-cache-design.md`

目标：全市场预测特征和风险上下文只计算一次并保存到独立硬盘缓存表。只要行情内容和算法版本没有变化，服务重启后搜索 INTC、NBIS 等股票直接读取缓存，不再承担约 50～60 秒的全市场重算。

### 本轮实现

- [x] 建立独立 `data/analysis_cache.db`，不得把缓存表写入原始行情库 `data/prices.db`。
- [x] 建立 `forecast_artifacts` 表，保存全市场特征表、风险上下文、评估结果、行情覆盖元数据和内容指纹。
- [x] 缓存键包含行情内容签名、Ridge 模型版本、特征版本、风险上下文版本和持久化格式版本。
- [x] 缓存命中后从硬盘恢复 DataFrame，并重新构造、验证 `RidgeForecastProvider`；不序列化运行时 provider。
- [x] 使用事务 UPSERT、payload checksum 和完整构建后发布。
- [x] 缓存损坏、SQLite 锁定、磁盘只读、未知格式或反序列化失败时安全退回冷构建，不向网页暴露内部异常。
- [x] 默认最多保留最近两个 artifact；过期版本自动清理，缓存文件可安全删除并重建。
- [x] 自定义测试 provider/evaluator 默认不落盘，显式注入 store 时才参与持久化测试。
- [x] 提供 `ForecastService.prewarm(histories)` 和 `build_forecast_cache.py`，预热最近两个活跃观察日 cohort。
- [x] 覆盖首次写入、全新进程命中、行情新增、同形状历史修订、模型/特征/风险版本、损坏恢复、写入失败、容量和并发回归测试。
- [x] 2026-07-26 完整本地库实测：首次生成 97,080 行特征和 19,061 行风险上下文耗时 62.187 秒，缓存约 12 MB；全新进程 INTC 首次请求 2.231 秒，同进程热请求 0.958 秒。

### 后续持续优化

- [x] 行情更新成功后自动预热已拆分为 `PERF-003` 独立任务；预热失败不能回滚已经成功写入的行情。
- [x] 在网页显示缓存状态：命中、重建中、上次生成时间、对应行情日期和算法版本，避免用户把后台重建误认为网页卡死。
- [x] 增加 `manage_analysis_cache.py` 缓存维护命令：`status` 查看预测/入场信号条目与磁盘占用，`verify` 校验全部 payload checksum，`prune` 默认只预览并要求显式 `--apply` 才按保留数量清理，`prewarm` 复用现有预测预热流程。2026-07-26 对真实缓存只读验收：2 个预测 artifact、11 个入场信号 artifact、13/13 checksum 有效、数据库及 WAL/SHM 共约 71.9 MiB，默认保留策略无需删除。
- [ ] 记录命中率、读取耗时、重建耗时、payload 大小和失败次数，形成可比较的性能基线。
- [ ] 若单一压缩 payload 读取仍偏慢，再评估把特征表、风险上下文和评估结果拆为独立 artifact，按需读取。
- [ ] 若 SQLite BLOB 超过可接受规模，再比较 Parquet/Arrow 文件加 SQLite manifest；迁移前必须以真实读取时间和磁盘占用为依据。
- [ ] 研究在全市场同一观察日只拟合每个 horizon 一次并批量预测全部股票，减少每只股票仍需执行的 Ridge 拟合。
- [ ] 评估为最新交易日预生成所有股票的最终 forecast bundle；只有能保持点时因果和模型版本一致时才启用。
- [ ] 后续将个股摘要、图表、模型输出拆分为独立接口，允许价格图先展示、预测面板随后加载。
- [ ] 为缓存数据库设置容量预警与保留策略；不得让缓存成为原始行情或研究结果的唯一副本。
- [ ] 若未来部署多进程/多实例服务，引入跨进程文件锁或单独预热 worker，避免多个进程同时重建同一 artifact。

## P1 — 下跌筑底与向上反转状态模型（BOTTOM-001）

目标：复用现有支撑、供给压力、需求确认、向上早期反转、板块和大盘状态，建立具有多日记忆的因果筑底状态机。模型识别“下跌延续 → 接近潜在支撑 → 卖压衰竭观察 → 向上早期反转观察 → 向上结构反转确认 → 突破回踩确认/筑底失效”的过程，不预测精确最低价，不把规则分数解释为上涨概率。

### 状态、证据与失效

- [x] 先确认此前存在有效下降趋势；长期横盘、健康上涨中的普通回踩不得直接进入筑底状态。
- [x] 聚合 UI-001 的点时近端支撑区、支撑强度、距离与测试状态，但“接近支撑”不得单独升级为底部确认。
- [x] 复用 DEMAND-001 的卖方衰竭、买方承接、缩量更高低点、强势收盘、上涨放量、突破接受和突破延续，不重复计算同源因子。
- [x] 复用 SUPPLY-001 的供给压力总分作为反证，并在放量创新低或跌破冻结支撑时即时否决；后续仍需把各项供给原子条件逐项显示在筑底卡中。
- [x] 复用 REV-001 的更高低点、突破前高和突破下降阻力线，严格区分早期观察与结构确认。
- [ ] 纳入个股相对 QQQ/板块强弱、板块需求/供给状态和 CAN SLIM 大盘状态；环境缺失时降低覆盖率，不用当前分类或未来数据回填历史。
- [ ] 使用 5～10 个交易日的因果状态记忆，记录首次触发日、状态年龄、最高已确认阶段和证据衰减；不得每天从零开始。
- [ ] 明确定义筑底失效：再次放量创新低、收盘有效跌破支撑区、供给重新占优、突破失败或确认后无法在限定窗口内维持。
- [ ] 允许供给分和需求分同时偏高并输出“多空争夺”，不得把需求分简单定义为 `100 - 供给分`。
- [x] 输出 0～100 规则证据分、覆盖率、五组子分、已满足证据、反证和冻结失效位；规则分数不是概率，也不直接覆盖 Ridge。
- [x] 将有效的历史需求支撑区只作为“支撑位置”证据写入筑底诊断；不得重复加入当日买盘确认分。

2026-07-30 冻结研究结论：

## P1 — 高位派发与顶部向下转折风险模型（TOPRISK-001）

### 高位背景门控

### 2026-07-29 冻结实验结论

- 使用 `data/research_prices.db`，冻结在 2026-07-24；从 2018-01-01 起评估 240 只确定性抽样股票，其中 235 只满足至少 220 个交易日，形成 4,090,301 条 5/10/20 日成熟观察。
- 主门槛采用 10 日重叠样本，并严格限定为同一股票、同一观察日、同一周期的配对比较；增强模型与基线各有 308,947 条配对样本。
- 基线支撑守住率为 42.28%，加入历史需求区后为 40.82%，下降 1.46 个百分点；5 日和 20 日也分别下降 1.85 和 1.18 个百分点。
- 半导体、软件、其他三组的 10 日增量分别为 -1.36、-1.14、-1.80 个百分点；5 个时间折中的三个分组全部为负，没有稳定折胜出。
- 相同观察日的最大有利/不利波动和最终收益天然一致，因此不能拿这些字段为区域替换制造虚假优势；它们只用于审计未来路径。新增覆盖样本单独归入 `all_eligible`，不得混入配对晋级票数。
- `no_environment` 与 `no_retests` 的守住率高于完整历史需求模型，`no_decay` 略低，说明 40 日衰减仍有保留价值，但环境确认和回踩奖励需要重新定义。`no_volume` 无法形成合格事件，证明当前事件生成强依赖成交量，但不构成独立性能优势。
- 晋级结论：`stable_fold_wins=0`，三个板块均未改善，增量为负；现有历史板块区间还带有 `historical_backfill_assumption`，所以点时分组因果审计也失败。模型继续保持 `research` / `advisory`，不得进入 Ridge、向下否决或最终方向策略。
- 研究产物：`reports/historical-demand-support-study.md`、`reports/historical-demand-support-study.csv`、`reports/historical-demand-support-study.json`。
